# Review v3 — 계산서함 자동인식 정확도 개선 2건 독립 검증

이 문서는 `apps/settlement/invoices.js`에 이전 세션들이 적용했다고 보고한 두 차례 수정
① "세금계산서가 아닌 문서(거래명세표 등) 조용히 무시" ② "자동인식 정확도 개선 4건"을,
그 수정을 만든 에이전트가 아닌 별도 Review 에이전트로서 직접 재현 테스트하여 검증한 결과다.
이전 에이전트의 "19/19 단위 테스트 통과" 자체 보고는 신뢰하지 않고, 코드를 처음부터 다시
읽고 새로 설계한 테스트로만 판단했다.

## 검증 방법
1. `apps/settlement/invoices.js` 전체를 처음부터 끝까지 읽고 변경사항이 실제 코드에
   반영되어 있는지 확인.
2. `apps/settlement/invoices.js`의 순수 텍스트 처리 함수(`extractVendor`,
   `extractIssueDate`, `extractAmountNear`, `buildTextFromItems`, `isTaxInvoiceDocument`,
   `extractFieldsFromText` 등)를 그대로 복사해 Node.js 스크립트로 독립 재현 테스트 38건
   작성·실행(pdfjs-dist/브라우저 의존성이 있는 원본 모듈은 Node에서 직접 import 불가하므로,
   함수 본문을 한 글자도 바꾸지 않고 옮겨와 검증했고, 실제로 이번에 수정한 두 함수는
   invoices.js 원본과 최종적으로 동일한 로직임을 재확인함).
3. Python(reportlab)으로 실제 전자세금계산서와 유사한 PDF 6종을 새로 생성해, 정적 서버
   (`http://localhost:8000/apps/settlement/invoices.html`)를 브라우저로 띄운 뒤
   드래그앤드롭 이벤트를 실제로 발생시켜 **pdf.js 추출 → 자동인식 → localStorage 저장**
   전체 파이프라인을 엔드투엔드로 통과시켜 결과를 확인함(이전 에이전트의 테스트를 재사용하지
   않고 전부 새로 설계).
4. `git status`로 이번 세션에서 실제로 수정한 파일이 `apps/settlement/invoices.js` 하나뿐임을
   확인(다른 파일들의 M/?? 상태는 이전 세션에서 이미 그 상태였고, 이번 세션이 손대지 않음).

## 검증 결과

### 통과한 항목
- **거래명세표/거래명세서 조용히 무시**: `isTaxInvoiceDocument()`가 텍스트 경로/OCR 경로
  양쪽에서 호출되고, `false`면 임시 행을 목록에서 제거함을 코드로 확인. "거래명세표" 제목
  PDF를 실제 업로드했을 때 목록에 전혀 나타나지 않고 콘솔 에러도 없음을 브라우저에서 확인.
- **인식 실패 행(필수 4개 중 3개 이상 공란) 목록 제외**: 저품질 텍스트 PDF를 실제 업로드해
  목록에 추가되지 않음을 확인. 2개만 비어있는 경계 케이스는 목록에 남아 "확인 필요"로 뜨는
  것도 확인(과잉 무시 방지).
- **"상호"/"(법인명)" 사이 공백·줄바꿈, 그리고 "상호"·"(법인명)"·회사명이 PDF 안에서 아예
  서로 다른 텍스트 아이템으로 분리된 실제 케이스**: 새로 만든 PDF(라벨과 값을 별도
  `drawString` 호출 3개로 분리)를 업로드해 거래처가 "(법인명)"이 아니라 실제 회사명
  "분리테스트건설"로 정확히 채워짐을 확인.
- **발행일: 무관한 날짜형 숫자보다 라벨 우선 + 연도 범위 검증**: "문서번호 1904-07-08-XG991"
  이 작성일자보다 먼저 나오는 PDF를 업로드해 실제 작성일자(2024-09-03)를 정확히 뽑아냄을
  확인.
- **`extractVendor`의 "(법인명)" 폴백 토큰 탐색 루프**: 반복된 "(법인명)" 토큰이나 값이
  전혀 없는 입력에서도 무한루프 없이 즉시 종료함을 확인(별도 시간 측정 테스트 포함).
- **회귀 확인**: `git status`로 이번 세션이 `invoices.js` 외 어떤 파일도 건드리지 않았음을
  확인했고, "잘 인식되는" 정상 계산서 케이스도 여전히 정확히 인식됨을 재확인. `index.html`
  (정산서 작성 화면)은 이번 수정과 무관.

### 발견해서 수정한 문제 2건

**문제 1 (핵심 버그) — `buildTextFromItems`가 표 형태 PDF에서 서로 다른 셀의 텍스트를
공백 없이 그대로 이어붙임.**
실제 세금계산서 PDF는 "년/월/일/공급가액/세액/비고" 같은 컬럼들이 서로 다른 PDF 텍스트
아이템으로 분리되어 있고, 셀 사이 여백은 시각적 간격일 뿐 텍스트에 공백 문자가 없는 경우가
흔하다. 기존 `buildTextFromItems`는 x좌표로 정렬은 하지만 `join('')`으로 그냥 이어붙였기
때문에, 헤더 행이 "년월일공급가액세액비고"로, 값 행이 "24"+"06"+"15"+"10,000,000"+
"1,000,000" → "24061510,000,0001,000,000"으로 전부 한 덩어리가 되어버렸다. 그 결과
`extractAmountNear`가 공급가액/세액에 거대한 쓰레기 숫자(예: 240615100000001000000)를
채워 넣는 것을 reportlab으로 만든 재현 PDF를 실제 브라우저에 업로드해 직접 확인했다.
→ **수정**: 같은 줄 안에서 x좌표 정렬 후 이어붙일 때, 이전 아이템의 오른쪽 끝(x+width)과
다음 아이템의 x좌표 사이에 1pt를 넘는 간격이 있으면 공백 한 칸을 삽입하도록 변경(코드 내
주석에 근거와 임계값 선정 이유 기술). 폰트 분할로 한 단어가 여러 아이템으로 쪼개진 경우
(간격이 0에 가깝거나 음수)는 공백을 넣지 않아 그런 경우까지 잘못 갈라놓지 않는다.

**문제 2 — `extractAmountNear`의 "다음 줄 첫 숫자" 폴백이 다중 컬럼 표에서 엉뚱한 컬럼을
집을 수 있음.**
문제 1을 고쳐 셀 사이에 공백이 보존되게 만든 뒤에도, 라벨이 있는 줄과 값이 있는 줄이 분리된
헤더/값 2행 구조(국세청 전자세금계산서 표준 서식에서 흔함)에서는 "다음 줄의 첫 숫자"를
그냥 집는 방식이 "일(day)"이나 "년도" 같은 전혀 다른 컬럼 값을 집어올 수 있다(예: "년 월 일
공급가액 세액 비고" 헤더 다음 줄 "24 06 15 10,000,000 1,000,000"에서 공급가액/세액 모두
"24"로 오인식). → **수정**: 라벨 줄을 공백 기준으로 토큰화해 라벨이 몇 번째 토큰인지 찾고,
다음 줄도 같은 방식으로 토큰화해 같은 인덱스의 토큰을 우선 시도하는 `amountAtColumnIndex()`
함수를 추가. 표의 마지막 컬럼(비고 등)이 비어 있어 다음 줄 토큰 수가 더 적어지는 흔한
경우까지 커버하도록 "인덱스가 다음 줄 토큰 범위 안에만 들면 됨"으로 관대하게 처리했고,
컬럼 매칭이 실패하면 기존처럼 다음 줄 첫 숫자로 폴백한다.

두 수정 모두 `apps/settlement/invoices.js` 안에서만 이루어졌다. 수정 후 Node 재현
테스트 38건 전부 통과, 그리고 위 "국세청 표준 서식형 헤더/값 분리 레이아웃" PDF를 실제
브라우저에 다시 업로드해 공급가액 10,000,000 / 세액 1,000,000 / 합계 11,000,000이 정확히
채워짐을 재확인했다(원래 사용자가 겪었던 "부가세 15,000인데 합계가 54" 같은 증상과 근본
원인이 같은 계열의 버그였다).

## 브라우저 실측 재검증 요약 (6개 PDF 업로드)
| 파일 | 기대 동작 | 결과 |
|---|---|---|
| 정상 세금계산서 | 모든 필드 정확, needsReview=false | 통과 |
| 표(헤더/값 분리) 레이아웃 | 공급가액 10,000,000 / 세액 1,000,000 / 합계 11,000,000 | 수정 전 실패(거대 쓰레기값) → 수정 후 통과 |
| 거래명세표 | 목록에 나타나지 않음(조용히 무시) | 통과 |
| 저품질 텍스트 | 목록에 나타나지 않음(recognitionFailed) | 통과 |
| 날짜 함정(문서번호가 작성일자보다 먼저) | 작성일자만 정확히 채택 | 통과 |
| 상호 라벨/값이 별도 PDF 텍스트 아이템으로 분리 | 거래처 = 실제 회사명 | 통과 |

콘솔 에러 없음, 페이지 정상 로드·렌더링 확인. `index.html`(정산서 작성 화면)은 이번
수정 대상이 아니며 영향 없음.

## 최종 결론
이전 두 차례 수정("거래명세표 무시", "자동인식 정확도 개선 4건")의 의도된 동작 자체는
코드와 실측 모두에서 정상 확인되었다. 다만 그 수정들이 전제로 삼은 `buildTextFromItems`의
"컬럼 뒤섞임 방지"가 실제로는 불완전했고(셀 사이 공백 소실이라는 더 근본적인 버그가
남아 있었음), 이를 이번 리뷰에서 새로 발견해 `invoices.js` 안에서 직접 수정하고
재검증했다. 수정 후 Node 재현 테스트 38/38, 브라우저 실측 6/6 모두 통과했으며, 회귀
영향(다른 파일 미변경, 정상 계산서 케이스 유지)도 확인되었다. **정상 배포 가능**.
