# Build 서브에이전트 지침 — 계산서함: 실제 계산서 원문으로 금액 추출 로직 재작성

## 역할
너는 이 프로젝트(마크다운 블로그 + 미니 웹앱 포트폴리오)의 **Build 단계** 서브에이전트다.
`apps/settlement/invoices.js`의 금액(공급가액/세액/합계금액) 추출 로직을, 실사용자가 실제로 제공한 계산서 원문 텍스트를 근거로 다시 고치는 것이 임무다. 이번엔 추측이 아니라 **아래 실제 원문을 정확한 테스트 픽스처로 삼아** 그 값이 정확히 나올 때까지 반복 검증하라.

## 배경
지금까지 세 차례(사업자등록번호/발행일/거래처 오인식 수정, 표 컬럼 뒤섞임 수정, 라벨 자간 대응)를 고쳤지만, 실사용자의 실제 계산서에서는 여전히 공급가액/세액/합계금액이 전부 0으로 나온다. 사용자가 직접 계산서함의 "텍스트" 버튼(진단용으로 방금 추가됨, `invoices.js`의 `data-action="rawtext"` 핸들러 참고)으로 실제 추출된 원문을 복사해서 제공했다. 아래가 그 실제 원문이다(정확히 그대로):

## 원인 분석 (이미 파악됨, 참고만 하고 직접 코드로 재확인하라)
1. **금액(공급가액/세액) 부분**: 라벨 행("작성일자 공급가액 세액 수정사유 비고")과 실제 값 행("2026-07-31 350,000 35,000 해당없음 ...") **사이에 빈 줄이 하나 끼어 있다.** 지금 `extractAmountNear`/`amountAtColumnIndex`는 "라벨이 있는 줄의 바로 다음 줄"만 값 후보로 보기 때문에, 빈 줄 때문에 값 행을 못 찾는 것으로 추정된다.
2. **합계금액**: 라벨 행("합계금액 현금 수표 어음 외상미수금") 바로 다음 줄이 값이 아니라 "이 금액을 (청구) 함"이라는 고정 문구이고, **그 다음에야** 385,000이라는 숫자가 **그 줄 하나에 단독으로** 나온다. 즉 합계금액은 라벨로부터 2줄(빈 줄까지 포함하면 더) 떨어져 있고, 그 사이에 무관한 텍스트가 낀다.

## 범위 제한 (매우 중요)
- **오직 `apps/settlement/invoices.js` 파일만 수정한다.**
- 다른 파일은 절대 건드리지 않는다.

## 시작 전 필수: 기존 코드 읽기
`apps/settlement/invoices.js` 전체를 읽어라. 특히 `extractAmountNear`, `amountAtColumnIndex`, `tokenizeWithOffsets`, `collapseKnownLabelGaps`, `extractVendor`, `extractFieldsFromText`를 정확히 파악하라.

## 고칠 것

### 1. 라벨 줄과 값 줄 사이의 빈 줄(들)을 건너뛰도록 수정
"라벨이 있는 줄의 바로 다음 줄"만 보던 로직을, **빈 줄(공백만 있거나 완전히 빈 줄)은 건너뛰고 그다음 내용이 있는 줄**을 후보로 삼도록 고쳐라. 컬럼 인덱스 매칭(`amountAtColumnIndex`)도 이 "다음 내용 있는 줄"을 값 줄로 사용하도록 연결하라.

### 2. 라벨에서 여러 줄 떨어져 있고 사이에 무관한 텍스트가 낀 값(특히 합계금액) 처리
라벨을 찾은 뒤, 값을 "바로 다음 유효한 줄" 하나만이 아니라 **다음 몇 개 줄(예: 최대 5줄) 안에서** 찾도록 탐색 범위를 넓혀라. 이때:
- 먼저 각 후보 줄에 대해 컬럼 인덱스 매칭을 시도하고,
- 그것이 실패하면, **그 줄 자체가 숫자(쉼표 포함)만으로 이루어진 줄인지**(trim 했을 때 `/^[\d,]+$/`에 매치되는지)를 우선적으로 확인해 있으면 그 값을 채택하고,
- 그것도 아니면 기존처럼 그 줄에서 라벨 뒤(혹은 줄 전체)의 첫 숫자 패턴을 채택하는 폴백을 유지하라.
- 순서상 상식적인 제약을 둬라: 예를 들어 "공급가액"을 찾다가 엉뚱하게 저 멀리 떨어진, 전혀 다른 항목의 숫자를 잘못 채택하지 않도록, 컬럼 매칭이 되는 줄을 최우선으로 하고 "숫자만 있는 단독 줄"은 그다음 우선순위로 두는 등 합리적인 순서를 스스로 설계하라.

### 3. 거래처(상호) 추출 시 회사명에 공백이 포함되고 뒤에 다른 라벨이 곧바로 이어 붙는 경우
`extractVendor`가 "상호" 라벨 뒤에서 값을 찾을 때, 지금처럼 공백 기준 토큰 하나만 잡지 말고, **"성명"이라는 다음 라벨이 나오기 전까지의 텍스트 전체**(공백이 있어도 됨)를 회사명으로 잡도록 개선하라(단, 끝의 불필요한 공백은 trim). "성명" 라벨이 없는 다른 형태의 계산서(회사명이 한 토큰인 경우)에서는 기존처럼 동작해야 한다(회귀 없음).

### 4. 공급자/공급받는자 블록 판별이 이 문서에서도 정확히 동작하는지 재확인
이 문서는 "공급자"/"공급받는자" 라벨이 극단적으로 세로로 쪼개져 있다(글자마다 줄바꿈). `sliceBetween`이 이런 경우에도 "공급자" 블록과 "공급받는자" 블록을 정확히 나누는지, 그래서 사업자등록번호 `506-81-62240`(공급자)이 `374-87-02119`(공급받는자)보다 먼저/정확히 채택되는지 실제로 이 원문을 넣어 확인하라.

## 검증 (필수 — 반드시 위에 제공된 실제 원문 텍스트로 직접 확인)
Node.js로 위 원문 텍스트를 그대로 문자열 상수로 넣고 `extractFieldsFromText()`를 호출해서, 결과가 정확히 다음과 일치하는지 확인하라:
```
issueDate: "2026-07-31"
vendor: "주식회사 신풍중기"
bizRegNo: "506-81-62240" (formatBizRegNo 형식대로)
supplyAmount: 350000
vat: 35000
total: 385000
needsReview: false (모든 필수 필드가 채워지고 금액이 정합하므로)
```
정확히 일치할 때까지 반복 수정하라. 그다음 아래도 재확인하라:
- 이전 리뷰들(review-v3-accuracy.md, review-v4-label-spacing.md)이 확인한 시나리오들이 이번 수정 이후에도 여전히 통과하는지(회귀 없음) — 특히 "표 컬럼 매칭" 관련 테스트는 "라벨 줄 바로 다음 줄"이 아니라 "몇 줄 뒤"까지 보게 된 것이 잘못된 값을 잘못 채택하게 만들지 않는지 신경 써서 확인하라.
- `node --check apps/settlement/invoices.js`로 문법 검증.
- 브라우저에서 `invoices.html`이 콘솔 에러 없이 로드되는지 확인.
