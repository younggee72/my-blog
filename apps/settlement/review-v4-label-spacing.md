# Review v4 — 계산서함 라벨 자간(공백) 대응 수정 독립 검증

이 문서는 `apps/settlement/invoices.js`에 적용된 "라벨 글자 사이 자간 공백에
관대한 탐색으로 전환"(`buildLooseLabelSource`/`buildLooseLabelRegex`/
`findLooseLabel`, `LABEL_GAP_MAX = 4`) 수정을, 그 수정을 만든 에이전트가 아닌
별도 Review 에이전트로서 직접 재현 테스트로 검증한 결과다. 이전 에이전트의
"17/17 단위 테스트 통과" 자체 보고는 신뢰하지 않고, 코드를 처음부터 다시
읽고 새로 설계한 테스트만으로 판단했다.

## 검증 방법
1. `invoices.js` 전체(1300줄)를 처음부터 끝까지 읽고 이번 수정이 건드린
   함수(`sliceBetween`, `extractVendor`, `extractIssueDate`,
   `extractAmountNear`, `amountAtColumnIndex`/`tokenizeWithOffsets`,
   `isTaxInvoiceDocument`)를 전부 확인.
2. 순수 텍스트 처리 함수를 한 글자도 바꾸지 않고 그대로 옮겨 Node.js
   재현 테스트 32건을 새로 작성·실행(이전 에이전트의 테스트는 재사용하지
   않음). pdfjs-dist/DOM 의존성이 있는 원본 모듈은 Node에서 직접 import할
   수 없어 순수 함수만 분리해 검증했다.
3. 정적 서버(`http://localhost:8000/apps/settlement/invoices.html`)를
   브라우저로 열어 콘솔 에러 없이 로드되는지 확인.
4. `git status`/`git diff`로 이번 세션이 실제로 수정한 파일 범위를 확인.

## 발견해서 수정한 문제 1건

**`amountAtColumnIndex`가 헤더 행의 "다른" 라벨도 자간이 섞여 있을 때
컬럼 인덱스를 잘못 계산함.**

재현 테스트로 다음 헤더/값을 넣어보았다:
```
년 월 일 공  급  가  액 세  액 비고
24 06 15 10,000,000 1,000,000
```
`세액`을 찾을 때, 함수는 `labelLine`을 `\S+` 기준으로 토큰화해 "라벨이 몇
번째 토큰인가"로 컬럼 인덱스를 셌다. 그런데 그보다 **앞에 나오는** `공급가액`
라벨도 자간 때문에 `공`/`급`/`가`/`액` 4개의 개별 토큰으로 쪼개지면서, `세액`
앞에 실제 컬럼 수(년/월/일/공급가액=4번째)보다 많은 토큰(7번째)이 있는 것으로
계산됐다. 그 결과 `idx=7`이 값 행의 토큰 범위(5개)를 벗어나 `null`을
반환하고, 상위 `extractAmountNear`는 "다음 줄 첫 숫자" 폴백으로 떨어져
`일(day)` 컬럼 값인 `24`를 세액으로 잘못 채택했다(재현 스크립트로 직접
확인, `got=24`).

이 시나리오는 인위적이지 않다 — 국세청 표준 서식처럼 헤더 행 전체가 균일한
자간으로 인쇄되는 문서라면 `공급가액`뿐 아니라 `세액`/`합계금액` 등도
함께 자간이 들어가는 것이 오히려 자연스럽다. 즉 이번에 적용된 자간 대응
수정이 정확히 노리는 문서 유형에서, 그 수정이 새로 추가한 컬럼 매칭 로직
자체가 깨지는 조합이었다.

**수정**: `amountAtColumnIndex`가 헤더 토큰화 전에, 흔히 함께 등장하는
금액/비고 라벨(`공급가액`, `세액`, `부가세`, `합계금액`, `청구금액`, `비고`)의
느슨한 매치 구간 안 공백을 공백이 아닌 자리표시 문자(U+0000, 문자열 길이는
그대로 유지)로 미리 치환하는 `collapseKnownLabelGaps()`를 추가했다.
이렇게 하면 이런 라벨들은 `\S+` 토큰화에서 항상 하나의 토큰으로 셈해지므로,
그 앞에 자간 섞인 라벨이 몇 개 있든 실제 컬럼 개수와 토큰 개수가 일치한다.
문자열 길이를 유지했기 때문에, 원본 `labelLine`에서 `buildLooseLabelRegex`로
찾은 매치 시작 위치(`matchStart`)는 그대로 유효하다.

수정 후 동일 재현 케이스, 그리고 세 라벨(공급가액/세액/합계금액) 모두 자간이
섞인 3컬럼 케이스, 자간 섞인 헤더 + 마지막 컬럼(비고)이 비어 값 행 토큰
수가 더 적은 케이스까지 추가로 테스트해 모두 정확한 값을 뽑아냄을 확인했다.

## 발견했지만 코드를 고치지 않은 한계 (설계상 트레이드오프로 판단)

**`LABEL_GAP_MAX=4`는 "라벨 글자들이 무관한 텍스트 중간에 우연히 정확한
순서로, 공백만으로(다른 문자 섞임 없이) 4칸 이하 간격으로 나열되는" 극단적
경우를 걸러내지 못한다.** 재현 테스트로 다음과 같은 텍스트를 넣으면
`isTaxInvoiceDocument`가 `true`로 오판된다:
```
...회의록입니다. (반복) 세    금    계    산    서 라고 적어보았지만...
```
다만 이 경우는 "세","금","계","산","서" 5글자가 **다른 문자의 개입 없이,
공백만으로** 순서대로 이어져야 하므로(정규식이 `\s`만 허용하고 임의의 문자는
허용하지 않음), 실제 업무 문서/스캔 텍스트에서 우연히 이런 배열이 나올
가능성은 매우 낮다고 판단했다(3-3 테스트에서 확인했듯, 글자 사이에 조금이라도
다른 문자가 끼면 전혀 매치되지 않는다 — 예: "우리 세 무팀은 금 년도..."는
매치되지 않음). 이를 완전히 막으려면 "주변 문맥"까지 봐야 하는 더 복잡한
휴리스틱이 필요한데, 그러면 정작 이번 수정이 해결하려던 "저품질 OCR/자간
서식 문서에서 라벨을 못 찾는" 문제의 재현율이 다시 떨어질 위험이 크다.
정밀도(오탐 방지)와 재현율(실제 자간 라벨 인식) 사이의 의도적 트레이드오프로
보고 코드는 그대로 두었다. 향후 실사용 중 유사 오탐 사례가 실제로 보고되면
그때 임계값을 낮추거나(예: 3) 문맥 검증을 추가하는 편이 낫다고 판단한다.

`LABEL_GAP_MAX=4` 자체는 1~4칸의 다양한 자간 테스트에서 전부 정상 추출됐고,
너무 엄격해서 실제 자간을 못 잡는 사례는 발견하지 못했다.

## 최종 결론
이번에 적용된 라벨 자간 대응 수정(`buildLooseLabelSource`/
`buildLooseLabelRegex`/`findLooseLabel`)은 의도한 대로 동작하며, 자간 없는
기존 케이스에도 회귀가 없다. 다만 그 수정이 새로 열어놓은 "표 컬럼 매칭에서
헤더 행의 다른 라벨도 자간이 섞이면 컬럼 인덱스가 틀어지는" 버그를 이번
리뷰에서 새로 발견해 `invoices.js` 안에서 `collapseKnownLabelGaps()`로
직접 수정하고, 추가 케이스(3컬럼 동시 자간, 마지막 컬럼 공란)까지 재검증했다.
"세금계산서 5글자가 공백만으로 우연히 나열되는" 극단적 오탐 가능성은
설계상 한계로 확인했으나, 실제 발생 가능성이 매우 낮고 이를 막으려는 시도가
본래 목적(자간 서식 인식률 개선)을 해칠 위험이 커서 의도적으로 남겨두었다.
재현 테스트 32/32 통과, 브라우저 콘솔 에러 없음, 수정 범위는
`apps/settlement/invoices.js` 한 파일로 한정됨을 확인했다. **정상 배포
가능.**
