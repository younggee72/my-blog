# Plan 서브에이전트 지침 — 법인차량 관리 프로그램

## 역할
너는 이 프로젝트(마크다운 기반 블로그 + 미니 웹앱 포트폴리오, HTML/CSS/JS만 사용)의 **Plan 단계** 서브에이전트다.
아래 요구사항을 바탕으로 구현 계획을 세우고, `apps/vehicle-fleet/spec.md` 파일로 저장하는 것이 유일한 임무다.
**코드를 작성하지 마라.** 계획 문서만 작성한다.

## 프로젝트 제약 조건
- 마크다운 기반 블로그 + 미니 웹앱 포트폴리오, HTML/CSS/JS만 사용, 빌드 도구/번들러 없음.
- 모든 웹앱은 `/apps/{앱이름}/` 폴더 안에 자체 완결된다.
- 외부 라이브러리 사용을 최소화한다. CDN은 허용된다.
- 모바일에서도 사용할 수 있어야 한다.
- 모든 웹앱은 블로그의 색상 팔레트를 따른다. `/css/style.css`의 CSS 변수를 참조할 것.
- 웹앱에 사용법 안내 문구를 반드시 포함한다.

## 웹앱 공통 규칙
- 모든 웹앱은 `apps/vehicle-fleet/` 폴더 안에 자체 완결되어야 한다. 프로젝트의 다른 파일(`index.html, post.html, /css/, /js/, /posts/, 다른 apps/*/`)은 건드리지 않는다.
- 외부 라이브러리 사용을 최소화한다(CDN은 허용되지만 대부분의 경우 불필요하다).
- 모바일에서도 사용 가능해야 한다(터치 입력 등 고려).
- 다크 모드를 지원해야 한다(`prefers-color-scheme` 자동 대응 + `[data-theme]` 속성 + localStorage 토글, 블로그 본체의 `js/theme.js`와 동일한 방식).
- 사이트의 색상 팔레트를 따라야 한다. `/css/style.css`의 `:root` CSS 변수(`--color-bg`, `--color-bg-secondary`, `--color-text`, `--color-text-secondary`, `--color-accent`, `--color-border`, `--color-code-bg`, `--font-body`, `--font-mono`)를 그대로 참조할 것.
- 화면 안에 사용법 안내 문구를 반드시 포함해야 한다(별도 도움말 페이지가 아니라, 앱을 열자마자 보이는 짧은 안내).

## 사용자 요청
"법인차량 관리 프로그램을 만들고 싶어. 우리 회사에 법인차량이 포터 6대, 2.5톤 덤프 1대, 포크레인 1대, 승용차 1대 있어. 1. 검사주기 2. 엔진오일 등 각종 오일 확인 등등 관리 기능부터 계획을 잡자."

요구사항:
- 대상 차량: 포터(트럭) 6대, 2.5톤 덤프트럭 1대, 포크레인(굴착기) 1대, 승용차 1대 — 총 9대. 각 차량은 차량번호(번호판), 차종, 담당자/운전자, 비고 등을 등록·수정·삭제할 수 있어야 한다. 포크레인처럼 도로 주행이 없는 중장비도 등록 가능해야 한다(단, 자동차검사 대신 건설기계 정기검사 항목을 다르게 표시할 수 있으면 좋다).
- **검사주기 관리**: 자동차 정기검사(승용차/포터/덤프는 자동차관리법상 정기검사, 포크레인은 건설기계 정기검사)와 보험(자동차보험/건설기계보험) 만기일을 차량별로 등록하고, 마지막 검사/가입일 + 주기(개월)로 다음 예정일을 자동 계산하거나 다음 예정일을 직접 입력할 수 있어야 한다. 만기 임박(예: 30일 이내)·만기 경과 항목은 목록에서 눈에 띄게(색상/배지) 표시한다.
- **오일/소모품 교환주기 관리**: 엔진오일, 미션오일(변속기오일), 유압오일(포크레인 등 중장비용), 에어필터, 오일필터, 타이어 등 항목별로 마지막 교환일(또는 교환 시 주행거리)과 교환주기(개월 또는 km)를 등록하고 다음 교환 예정을 계산해 임박/경과 여부를 표시한다. 차종에 따라 관리 항목이 다를 수 있음을 고려한다(예: 포크레인은 유압오일이 중요, 승용차/포터/덤프는 엔진오일·미션오일 중심).
- 전체 현황을 한눈에 볼 수 있는 대시보드(차량 목록 + 임박/경과 항목 요약)와 차량별 상세 화면을 둘 다 고려한다.
- 데이터는 서버 없이 브라우저에 저장한다(localStorage). 데이터 내보내기/가져오기(JSON) 또는 초기 샘플 데이터(포터 6대 등 실제 대수에 맞는 목업)를 포함할지 계획에서 판단해서 제안한다.
- 향후 차량 추가/변경이 쉬워야 한다(차량 대수나 차종이 바뀔 수 있음을 염두에 둔 데이터 구조).

## 산출물
`apps/vehicle-fleet/spec.md` 파일 하나를 작성한다. 내용에는 다음이 포함되어야 한다:

1. **개요**: 앱 설명 한두 문단.
2. **파일 구조**: `apps/vehicle-fleet/` 안에 만들 파일 목록과 각 파일의 역할.
3. **핵심 로직 설계**: 데이터 구조(차량, 검사/보험 항목, 소모품 항목의 스키마), 다음 예정일/임박 여부 계산 로직, localStorage 저장 방식, 초기 샘플 데이터 구성안.
4. **입력 처리**: 차량 등록/수정/삭제, 검사·소모품 항목 등록/수정/삭제 등 폼 입력을 어떻게 처리할지. 모바일에서 폼 입력이 쓰기 편한지 고려.
5. **UI/디자인**: 대시보드 레이아웃, 차량 상세 화면 레이아웃, 임박/경과 상태를 색상으로 어떻게 구분할지, 다크모드 대응, 팔레트 CSS 변수 참조 방식, 반응형 고려사항, 사용법 안내 문구를 어디에 어떻게 배치할지.
6. **작업 순서(체크리스트)**: Build 단계에서 순서대로 구현할 수 있도록 번호가 매겨진 단계별 작업 목록. 각 단계는 한 번에 검증 가능한 크기로 쪼갠다.

계획을 다 작성했으면 `apps/vehicle-fleet/spec.md`로 저장하고, 무엇을 작성했는지 간단히 요약해서 보고하라 (300자 이내).
