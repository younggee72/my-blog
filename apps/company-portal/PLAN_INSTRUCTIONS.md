# Plan 서브에이전트 지침 — 회사 홈페이지(사내 포털)

## 역할
너는 이 프로젝트(마크다운 기반 블로그 + 미니 웹앱 포트폴리오, HTML/CSS/JS만 사용)의 **Plan 단계** 서브에이전트다.
아래 요구사항을 바탕으로 구현 계획을 세우고, `apps/company-portal/spec.md` 파일로 저장하는 것이 유일한 임무다.
**코드를 작성하지 마라.** 계획 문서만 작성한다.

## 프로젝트 제약 조건
- 마크다운 기반 블로그 + 미니 웹앱 포트폴리오, HTML/CSS/JS만 사용, 빌드 도구/번들러 없음.
- 모든 웹앱은 `/apps/{앱이름}/` 폴더 안에 자체 완결된다.
- 외부 라이브러리 사용을 최소화한다. CDN은 허용된다.
- 모바일에서도 사용할 수 있어야 한다.
- 모든 웹앱은 블로그의 색상 팔레트를 따른다. `/css/style.css`의 CSS 변수를 참조할 것.
- 웹앱에 사용법 안내 문구를 반드시 포함한다.

## 웹앱 공통 규칙
- 모든 웹앱은 `apps/company-portal/` 폴더 안에 자체 완결되어야 한다. 프로젝트의 다른 파일(`index.html, post.html, /css/, /js/, /posts/, 다른 apps/*/` — 특히 기존 `apps/settlement/`, `apps/vehicle-fleet/`)은 건드리지 않는다.
- 외부 라이브러리 사용을 최소화한다.
- 모바일에서도 사용 가능해야 한다(터치 입력 등 고려).
- 다크 모드를 지원해야 한다(`prefers-color-scheme` 자동 대응 + `[data-theme]` 속성 + localStorage 토글, 다른 앱들과 동일한 패턴).
- 사이트의 색상 팔레트를 따라야 한다. `/css/style.css`의 `:root` CSS 변수(`--color-bg`, `--color-bg-secondary`, `--color-text`, `--color-text-secondary`, `--color-accent`, `--color-border`, `--color-code-bg`, `--font-body`, `--font-mono`)를 그대로 참조할 것.
- 화면 안에 사용법 안내 문구를 반드시 포함해야 한다.

## 배경 — 이 앱의 성격
사용자는 이 프로젝트를 사내에서 쓰는 회사 홈페이지(포털)로도 쓰고 싶어 한다. 개인 블로그 홈(`index.html`)과는 별개로, 회사 업무용 허브 역할을 하는 새 화면을 `apps/company-portal/`에 만든다(사용자와 상의해 "허브 페이지" 구성으로 확정: 기존 앱은 링크/카드로 연결하고, 없는 기능만 새로 구현).

## 사용자 요청
"그 홈페이지에, 현장정산서 그리고 법인차량관리, 현재 진행중인 현장기재 하고 그리고 기타 등등 계획부터 잡자" + 후속 확인: "위 4개사항 다 필요해"(진행중인 현장 기재 항목 4가지 전부 포함 확정).

요구사항:
1. **허브 역할**: `apps/company-portal/index.html`을 열면 회사 업무용 대시보드가 보인다. 기존에 이미 구현된 두 앱을 카드로 연결한다:
   - **현장정산서 자동화 도구** → `../settlement/index.html` 로 링크(카드에 아이콘+제목+짧은 설명, 클릭 시 이동. iframe 미리보기는 선택사항 — 블로그 홈의 카드 패턴을 참고하되 이 포털에 맞게 판단).
   - **법인차량 관리** → `../vehicle-fleet/index.html` 로 링크.
   - 두 앱의 코드/데이터는 절대 건드리지 않는다. 단순 링크(및 원한다면 iframe 미리보기)로만 연결한다.
2. **진행중인 현장(신규 기능, 이 앱 안에 직접 구현)**: 회사가 현재 진행 중인 공사 현장을 등록·관리하는 기능. 사용자가 확정한 4가지 항목을 모두 포함해야 한다:
   - **기본 정보**: 현장명, 위치(주소), 착공일~준공예정일, 담당자(현장소장 등)
   - **진행상태**: 공정률(%) 또는 단계(예: 착공전/기초/골조/마감/준공 — Plan 단계에서 어느 쪽이 더 적합할지, 또는 둘 다 지원할지 판단해서 설계)
   - **금액 정보**: 계약금액, 기성고(청구/수금 현황) — 내부 관리용 민감 정보이므로, 목록에서는 요약만 보이고 상세를 펼쳐야 보이게 하는 등 UX상 실수로 노출되지 않도록 배려. 통화 단위(원) 표시, 천단위 구분.
   - **투입 장비/차량 연결**: `apps/vehicle-fleet/`에 이미 등록된 차량(포터 6대, 덤프 1대, 포크레인 1대, 승용차 1대) 중 이 현장에 투입된 차량을 표시/선택할 수 있어야 한다. **설계 방향을 반드시 spec.md에 명시**: 이 프로젝트는 정적 사이트이고 `apps/vehicle-fleet/`와 `apps/company-portal/`가 같은 오리진(도메인)에서 서빙되므로 브라우저 localStorage는 **경로가 달라도 같은 오리진이면 공유**된다는 점을 활용할 수 있다. 즉 `company-portal`이 `vehicle-fleet-vehicles`라는 localStorage 키를 **읽기 전용으로** 참조해 차량 목록을 드롭다운/체크박스로 보여주는 방식을 1안으로 검토하되, 이 경우 (a) `vehicle-fleet` 쪽 데이터 스키마가 바뀌면 깨질 수 있다는 위험, (b) `vehicle-fleet`를 한 번도 안 열어본 브라우저에서는 해당 키가 없어 빈 목록일 수 있다는 점을 감안해 **항상 폴백으로 차량번호를 직접 타이핑하는 자유 입력도 함께 제공**한다. 이 읽기 전용 연동이 "자체 완결" 원칙에 어긋나지 않는지 spec.md에서 트레이드오프를 명시적으로 설명하고 최종 설계를 결정하라(대안: 아예 자유 입력 텍스트로만 구현하고 "연결"은 시각적 표시만 제공하는 2안도 고려 가능 — 더 단순하고 안전함).
3. **기타 확장 여지**: 사용자가 "기타 등등"이라고 언급한 만큼, 향후 새 업무용 카드/기능을 쉽게 추가할 수 있는 구조(예: 카드 목록을 배열 상수로 관리하거나, 새 섹션을 쉽게 끼워 넣을 수 있는 레이아웃)로 설계한다. 이번 범위에서 "기타" 항목을 구체적으로 구현하지는 않되, 대시보드에 "추후 추가 예정" 형태의 자리 하나 정도는 남겨도 좋다(과하게 만들지 말 것).
4. 데이터(현장 목록)는 서버 없이 localStorage에 저장한다(`company-portal-sites` 등 별도 키, `vehicle-fleet`나 `settlement`의 키와 충돌하지 않게 접두사 구분).
5. 초기 샘플 데이터(진행중인 현장 1~2건 정도)를 포함해 처음 열었을 때 빈 화면이 아니게 한다.

## 산출물
`apps/company-portal/spec.md` 파일 하나를 작성한다. 내용에는 다음이 포함되어야 한다:

1. **개요**: 앱 설명 한두 문단(허브+현장관리 성격을 명확히).
2. **파일 구조**: `apps/company-portal/` 안에 만들 파일 목록과 각 파일의 역할.
3. **핵심 로직 설계**: 데이터 구조(현장 항목 스키마 — 기본정보/진행상태/금액/투입차량 4개 영역 모두 포함), localStorage 저장 방식, 차량 연동 설계(위 2번 항목의 읽기전용 연동 여부와 트레이드오프 결론), 초기 샘플 데이터 구성안.
4. **입력 처리**: 현장 등록/수정/삭제 폼, 차량 선택/입력 UI.
5. **UI/디자인**: 허브 카드 영역(기존 앱 링크) + 진행중인 현장 섹션 레이아웃, 금액 정보 노출 UX(민감정보 배려), 다크모드, 팔레트 CSS 변수 참조, 반응형, 사용법 안내 문구 배치, "기타 확장" 자리 배치.
6. **작업 순서(체크리스트)**: Build 단계에서 순서대로 구현할 수 있도록 번호가 매겨진 단계별 작업 목록. 각 단계는 한 번에 검증 가능한 크기로 쪼갠다.

계획을 다 작성했으면 `apps/company-portal/spec.md`로 저장하고, 무엇을 작성했는지 간단히 요약해서 보고하라 (300자 이내).
