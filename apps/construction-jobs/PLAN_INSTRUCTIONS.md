# Plan 서브에이전트 지침 — 건설현장 구인 플랫폼

## 역할
너는 이 프로젝트(마크다운 기반 블로그+미니 웹앱 포트폴리오, HTML/CSS/JS만 사용)의 **Plan 단계** 서브에이전트다.
아래 요구사항을 바탕으로 구현 계획을 세우고, `apps/construction-jobs/spec.md` 파일로 저장하는 것이 유일한 임무다.
**코드를 작성하지 마라.** 계획 문서만 작성한다.

## 프로젝트 제약 조건
- 프레임워크/번들러 없이 순수 HTML, CSS, JavaScript만 사용한다.
- 외부 라이브러리 사용을 최소화한다. CDN은 허용된다.
- 모바일에서도 사용할 수 있어야 한다.
- 모든 웹앱은 블로그의 색상 팔레트를 따른다.
- 웹앱에 사용법 안내 문구를 반드시 포함한다.

## 웹앱 공통 규칙
- 이 앱은 `apps/construction-jobs/` 폴더 안에 자체 완결되어야 한다. 프로젝트의 다른 파일(`index.html`, `post.html`, `/css/`, `/js/`, `/posts/`, 다른 `apps/*/` 폴더)은 건드리지 않는다.
- 외부 라이브러리 사용을 최소화한다(CDN은 허용되지만 대부분의 경우 불필요하다).
- 모바일에서도 사용 가능해야 한다(터치 입력 등 고려).
- 다크 모드를 지원해야 한다(`prefers-color-scheme` 자동 대응 + `[data-theme]` 속성 + localStorage 기반 수동 토글 패턴을 따를 것 — 사이트 본체와 동일한 방식).
- 사이트의 색상 팔레트를 따라야 한다. `/css/style.css`의 `:root` CSS 변수(`--color-bg`, `--color-bg-secondary`, `--color-text`, `--color-text-secondary`, `--color-accent`, `--color-border`, `--color-code-bg`)를 그대로 참조할 것. 이 앱 폴더 안에 자체 CSS 파일을 만들되, 색상 값은 하드코딩하지 말고 위 변수를 var()로 참조한다.
- 화면 안에 사용법 안내 문구를 반드시 포함해야 한다(별도 도움말 페이지가 아니라, 앱을 열자마자 보이는 짧은 안내).

## 데이터 저장에 대한 중요한 전제
이 프로젝트는 정적 사이트(빌드 도구·서버 없음)이므로 별도 백엔드/DB가 없다. 따라서 이 앱은 **브라우저 localStorage 기반**으로 동작하는 것을 기본 전제로 계획하라 (즉, "구인 플랫폼"이지만 실제로는 한 브라우저 안에서 공고를 등록/조회/필터링하는 클라이언트 사이드 데모/도구에 가깝다). 이 한계를 spec.md에 명시하고, 사용자가 이해할 수 있도록 "이 앱은 실제 다중 사용자 매칭 서비스가 아니라 로컬 저장 기반의 공고 관리·열람 도구"라는 점을 개요에 적어라. 필요하다면 "내보내기/가져오기(JSON export/import)" 같은 보조 기능으로 데이터 공유 한계를 완화하는 방안을 제안해도 좋다.

## 사용자 요청
"건설현장 구인 플랫폼을 만들고 싶어. 모집 직종은 목수, 철근공, 신호수, 잡부 등. 아직 구체적인 기능/UI는 정해지지 않아서 계획부터 잡아달라고 함."

요구사항:
- 모집 직종: 목수, 철근공, 신호수, 잡부 등 건설 현장 직종 (직종 목록은 확장 가능하게 설계할 것 — 하드코딩하되 추가하기 쉬운 구조)
- 공고 등록: 현장 관리자/구인자가 공고를 등록할 수 있어야 한다 (직종, 현장 위치/지역, 일당 또는 급여, 모집 인원, 작업 기간/날짜, 연락처, 상세 설명 등 필요한 필드를 스스로 설계해서 제안)
- 공고 조회/탐색: 구직자가 공고 목록을 볼 수 있어야 한다
- 직종별 필터링은 반드시 포함
- 지역별 필터링, 일당/급여 정렬 등 추가로 유용할 만한 필터/정렬 기능을 스스로 제안
- 공고 상세보기
- 반응형 모바일 UI (건설 현장 특성상 구직자는 스마트폰으로 볼 가능성이 높음을 고려)
- 데이터는 localStorage 기반 (위 "데이터 저장에 대한 중요한 전제" 참고), 샘플/시드 데이터를 몇 개 넣어서 처음 열었을 때도 빈 화면이 아니게 할 것을 제안

## 추가 요구사항 (v2 — 사용자 피드백 반영)
`apps/construction-jobs/spec.md`는 이미 1차로 작성되어 있다. 이번에는 **처음부터 다시 쓰지 말고, 기존 구조(개요/파일구조/핵심로직/입력처리/UI/체크리스트)를 유지한 채 아래 3가지 기능을 자연스럽게 통합**해서 spec.md를 개정하라.

사용자의 제품 비전: "배달앱이 생기면서 업체가 배달앱에 등록하지 않고서는 물건을 팔 수 없게 된 것처럼, 이 플랫폼도 구직자가 등록하지 않으면 일자리를 구하기 어렵다고 느낄 만큼 현실적인 곳이어야 한다. 동시에 구인업체는 자기 일 수준에 맞는 적정 가격에 적정 수준의 사람을 구하는 데 지장이 없어야 한다." 이 프로젝트는 서버/DB/회원가입이 없는 정적 앱이므로 실제 락인·매칭·후기 시스템은 만들 수 없지만, 아래 세 기능으로 그 컨셉을 **UX/데이터 설계 수준에서 시뮬레이션**한다:

1. **시세 가이드**: 공고 등록 폼에서 직종+지역을 선택하면, 현재 저장된(시드 포함) 같은 직종·지역 공고들의 평균 일당을 계산해 "이 직종/지역 평균 일당: OOO원" 형태로 실시간 표시한다. 입력한 일당이 평균보다 현저히 낮으면(예: 70% 미만) "시세보다 낮아 구인이 어려울 수 있습니다" 같은 경고 문구를, 과도하게 높으면 별도 안내는 없어도 되지만 필요시 참고용으로 표시해도 좋다. 평균 계산은 `jobs.js`의 순수 함수로 구현.
2. **신뢰 배지**: 공고 등록 시 "사업자등록/현장소장 확인" 같은 self-report 체크박스(예: `verified: boolean` 필드)를 추가하고, 체크된 공고는 카드와 상세보기에 "인증 현장" 배지를 표시한다. 이것이 실제 검증이 아니라 자기 신고 방식이라는 한계를 사용법 안내 문구에 명시한다. 후기/평점까지는 이번 범위에서는 과도하니, 배지 수준으로 제한한다(후기 시스템은 향후 확장 아이디어로 spec.md 개요/마지막에 짧게만 언급).
3. **지원하기 플로우**: 목록 카드 단계에서는 연락처를 바로 노출하지 않고, 상세보기 모달에 "지원하기" 버튼을 두어 그걸 눌러야 연락처(전화번호 등)가 화면에 펼쳐지도록 한다(별도 서버 인증은 없으므로 그냥 클릭 시 숨겨진 영역을 펼치는 UI 인터랙션이면 충분). 이 버튼을 통해 "등록/참여해야 다음 단계로 넘어간다"는 느낌을 시뮬레이션한다.

이 3가지 기능이 기존 파일 구조(`jobs.js`/`app.js`)의 어느 함수/섹션에 들어가는지, 데이터 구조(공고 객체)에 어떤 필드가 추가되는지(`verified`, 시세 계산에 필요한 값 등)를 기존 3.2/3.3/3.4/4/5 절에 통합해서 수정하고, 체크리스트(6절)에도 해당 단계를 추가하라. 기존에 있던 시드 데이터 설계는 `verified` 필드가 골고루 섞이도록(일부는 true, 일부는 false) 조정한다.

## 추가 요구사항 (v3 — 핵심 구조 반전)
`apps/construction-jobs/spec.md`는 v2까지 작성되어 있다. 이번에는 **앱의 등록 주체와 탐색 주체를 서로 뒤바꾸는** 구조 반전 요청이다. 처음부터 다시 쓰지 말고, 기존 문서 구조(개요/파일구조/핵심로직/입력처리/UI/체크리스트)를 유지한 채 아래 내용을 반영해서 전면 개정하라. 이미 만든 3가지 UX 컨셉(시세가이드/신뢰배지/컨택플로우)의 취지는 그대로 살리되, 적용 방향만 뒤집는다.

사용자의 요청 원문: "기존 구인 플랫폼은 현장/공장이 구인공고를 내면 구직자가 지원하는 방식인데, 나는 반대로 일이 필요한 사람이 자기 정보(직종, 나이, 근무기간, 일당)를 등록하면 현장/공장이 그 사람을 보고 컨택하는 구조로 만들고 싶다."

즉:
- **등록하는 주체가 바뀐다**: 지금까지는 "구인자(현장/공장)"가 공고를 등록하고 "구직자"가 목록을 보고 지원했다. 이제는 **"구직자"가 자기 프로필(구직 정보)을 등록**하고, **"구인자(현장/공장 담당자)"가 그 목록을 필터링해서 보고 컨택**하는 구조로 뒤집는다.
- **데이터 구조**: "공고(job posting)" 객체를 "구직 프로필(worker profile)" 객체로 재설계한다. 최소한 다음 정보를 포함하되 스스로 항목을 다듬어도 좋다: 직종(jobType, 기존 JOB_TYPES 재사용), 이름 또는 별칭, 나이(또는 연령대), 경력/숙련도, 근무 가능 시작일 및 근무 가능 기간(예: 단기/장기, 또는 몇 개월), 희망 일당(또는 희망 급여), 활동 가능 지역(regionMain 등 기존 지역 필드 재사용), 연락처, 자기소개/특이사항(자격증, 보유 장비 등), 등록일(createdAt).
- **시세 가이드의 방향 반전**: 기존에는 "구인업체가 공고 등록 시 적정 일당을 가늠"하는 용도였다. 이제는 **구직자가 프로필을 등록할 때, 같은 직종·지역의 다른 구직자들이 등록한 평균 희망일당을 보여줘서 자기 몸값을 시세에 맞게 책정**하도록 돕는 용도로 바뀐다. 너무 낮게 등록하면(평균의 70% 미만) "시세보다 낮게 등록하면 손해를 볼 수 있습니다" 류의 안내를, 너무 높으면(평균의 150% 초과) "시세보다 높아 컨택이 늦어질 수 있습니다" 류의 중립적 참고 안내를 표시한다.
- **신뢰 배지의 방향 반전**: 기존에는 "인증 현장"(구인업체 self-report)이었다. 이제는 **구직자가 자기 경력/자격을 self-report로 체크**하는 방식(예: "경력 증빙 가능", "자격증 보유" 등)으로 바꾸고, 목록/상세에 "인증 인력" 또는 유사한 배지로 표시한다. 실제 검증이 아닌 self-report라는 한계는 동일하게 안내 문구에 명시한다.
- **컨택 플로우의 방향 반전**: 기존에는 "구직자가 지원하기를 눌러야 구인업체 연락처가 열리는" 흐름이었다. 이제는 반대로 **목록/상세에서는 구직자 연락처를 바로 노출하지 않고, "컨택하기" 버튼을 눌러야(구인업체 입장에서 클릭) 그 구직자의 연락처가 펼쳐지는** 흐름으로 바꾼다. 즉 클릭 주체가 구인업체로 바뀔 뿐, 인터랙션 메커니즘(hidden → 버튼 클릭 시 펼침, 모달 재오픈 시 리셋)은 동일하게 재사용한다.
- **필터/정렬 항목**: 기존 직종/지역/일당 필터·정렬은 그대로 "구직자 목록"에 적용하되, 이제 정렬 기준 명칭도 "희망일당 낮은순/높은순"처럼 자연스럽게 다듬고, 나이대나 근무가능시기 필터를 추가로 제안해도 좋다.
- **UI 라벨 전면 수정**: "공고 등록" → "구직 등록"(또는 "인력 등록"), "공고 목록" → "인력 목록"(또는 "구직자 목록"), 앱 제목("건설현장 구인 게시판")도 이 반전된 컨셉에 맞게 다시 짓는다(예: "건설현장 인력풀" 등, 스스로 자연스러운 이름을 제안). 헤더/안내 문구/버튼 텍스트 등 "공고"라는 단어가 남지 않도록 전체적으로 재검토한다.
- **시드 데이터**: 기존 "공고" 시드 데이터를 "구직자 프로필" 시드 데이터로 재작성한다(직종/지역/나이/희망일당을 다양하게 분포).

이 반전이 spec.md의 개요(1절), 파일구조(2절), 핵심로직(3절, 특히 데이터 구조·시세가이드·시드데이터), 입력처리(4절), UI(5절), 체크리스트(6절) 전반에 일관되게 반영되어야 한다. "공고"라는 단어와 "구인업체가 등록"이라는 서술이 문서에 남아있지 않도록 전체를 다시 검토하며 고쳐라.

## 산출물
`apps/construction-jobs/spec.md` 파일 하나를 작성(개정)한다. 내용에는 다음이 포함되어야 한다:

1. **개요**: 앱 설명 한두 문단. (localStorage 기반이라는 한계와 그 이유를 명시)
2. **파일 구조**: `apps/construction-jobs/` 안에 만들 파일 목록과 각 파일의 역할.
3. **핵심 로직 설계**: 공고 데이터 구조(필드 목록과 타입), 직종 목록 정의 방식, localStorage 저장/조회 방식, 필터링/정렬 로직, 시드 데이터 설계.
4. **입력 처리**: 공고 등록 폼 입력 검증, 마우스/키보드/터치 등 처리 방법, 모바일에서 폼 사용성 고려.
5. **UI/디자인**: 레이아웃 구성(목록 화면, 등록 폼, 상세보기를 어떻게 배치할지 — 탭/모달/별도 화면 등), 다크모드 대응, 색상 팔레트를 어떤 CSS 변수로 참조할지, 반응형 고려사항(모바일 브레이크포인트), 사용법 안내 문구를 어디에 어떻게 배치할지.
6. **작업 순서(체크리스트)**: Build 단계에서 순서대로 구현할 수 있도록 번호가 매겨진 단계별 작업 목록. 각 단계는 한 번에 검증 가능한 크기로 쪼갠다.

계획을 다 작성했으면 `apps/construction-jobs/spec.md`로 저장하고, 무엇을 작성했는지 간단히 요약해서 보고하라 (300자 이내).
